# Аналіз та оптимізація виконання програми (Системне програмування)

**Досліджувана програма:** Множення квадратних матриць (\(C = A \times B\))  
**Розмір матриць:** 1024x1024 (тип `float`)  
**Середовище:** Ubuntu 24.04 (WSL2), компілятор GCC

---

## 1. Побудова FlameGraph виконання

### 1.1. Демонстрація процесу побудови

Для побудови FlameGraph використовувались інструменти `perf` та скрипти Брендана Грегга.

```bash
perf record -g ./matrix_mult
perf script > out.perf
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > flamegraph.svg
```

### 1.2. Пояснення (інтерпретація) отриманих на графіку результатів

На згенерованому графіку (див. `flamegraph.svg`) вісь Y відображає глибину стека викликів, а вісь X показує не хронологічний час, а *частку семплів* (відсоток від загального часу виконання).

Функція `multiplyMatrix` займає понад 99% ширини графіка. Це свідчить про те, що саме вона є "вузьким місцем" програми, на яке процесор витрачає майже весь час виконання. Відсутність високих стовпців над нею вказує на те, що функція не викликає інших "важких" процедур, а самостійно виконує всі обчислення всередині вкладених циклів.

## 2. Збір та пояснення статистики виконання (неоптимізована версія, `-O0`)

### 2.1. `/usr/bin/time --verbose ./matrix_mult`

- **User time:** ~15.04 с — час виконання безпосередньо коду програми (алгоритму множення).
- **System time:** ~0.01 с — накладні витрати ядра ОС мінімальні, оскільки програма є CPU-bound.
- **Maximum resident set size:** ~15744 KB — пікове споживання RAM (відповідає розміру трьох масивів 1024x1024 типу `float`).
- **Minor page faults:** ~3209 — "м'які" промахи сторінок. Виникають при першому зверненні до віртуальної пам'яті, коли ОС фізично виділяє сторінки в RAM для масивів.

### 2.2. `perf stat -d ./matrix_mult`

- **Cycles / Instructions:** ~59.3 млрд тактів та ~58.9 млрд інструкцій (IPC = ~0.99).
- **L1-dcache-load-misses:** 1.09 млрд промахів кешу L1.

**Пояснення:** У наївній реалізації (цикли `i-j-k`) матриця `B` зчитується по стовпцях. Оскільки в C++ масиви зберігаються по рядках (row-major), таке зчитування руйнує просторову локальність. Завантажена процесором кеш-лінія (64 байти) використовується лише на 4 байти, після чого дані відкидаються. Це генерує понад мільярд промахів кешу і змушує процесор простоювати в очікуванні даних з RAM.

### 2.3. `perf report` (after `perf record`)

Трасування підтвердило дані FlameGraph: переважна більшість процесорного часу припадає на цільову функцію, тоді як системні виклики та ініціалізація векторів займають частки відсотка.

## 3. Замір енерговитрат (Power consumption)

Через архітектурні обмеження WSL2 (відсутність прямого доступу до RAPL), вимірювання проводилось на хост-системі Windows за допомогою `HWiNFO64`. Логувався датчик **CPU Package Power** з інтервалом 2 секунди.

Час виконання програми склав 14.06 с. Згідно з логами (див. графік `matrix_mult_graph.png`), середнє фонове споживання становило ~7.41 Вт, а споживання під час роботи програми — ~15.44 Вт.

### 3.1. Енерговитрати системи при виконанні програми

E_sys = P_load * T = 15.44 Вт * 14.06 с ≈ 217.09 Дж.

### 3.2. Енерговитрати виключно досліджуваної програми

ΔP = 15.44 Вт - 7.41 Вт = 8.03 Вт (чисте додаткове споживання алгоритму).
E_prog = 8.03 Вт * 14.06 с ≈ 112.90 Дж.

## 4. Порівняння параметрів до та після оптимізації

Для оптимізації було змінено порядок циклів на `i-k-j` (для забезпечення послідовного доступу до пам'яті по рядках) та застосовано прапорці `-O3 -march=native`.

### 4.1. Пояснення різниці в асемблерному коді (див. скріншоти Compiler Explorer)

- **До оптимізації (`-O0`):** Компілятор генерує скалярні інструкції (`movss`, `mulss`, `addss`), які обробляють лише одне 32-бітне число за раз. Відбувається постійне звернення до стека (`[rbp...]`) та дорогі виклики `std::vector::operator[]` на кожній ітерації.
- **Після оптимізації (`-O3`):** Компілятор оптимізував доступ до пам'яті (замінив виклики методів на пряму арифметику вказівників у регістрах) і автоматично векторизував код, застосувавши розширення AVX.

### 4.1.1. Пояснення на прикладі інструкцій AVX-розширень (SIMD)

В оптимізованому коді з'явилися інструкції для роботи з 256-бітними регістрами (`ymm`):

- `vmovups` (Vector Move Unaligned Packed Single): завантажує одразу **8 чисел** (`float`) з оперативної пам'яті в регістр.
- `vfmadd213ps` (Vector Fused Multiply-Add Packed Single): за **один такт** процесора множить 8 упакованих чисел з одного регістра на 8 чисел з іншого, і додає результат до акумулятора. Це ключова причина стрімкого падіння кількості виконаних інструкцій.

### 4.2. Порівняння часу та інших показників (`perf stat`)

- **Час виконання:** Впав із 14.06 с до **0.14 с** (прискорення у 100 разів).
- **Кількість інструкцій:** Зменшилася з 58.9 млрд до **875 млн** (завдяки SIMD).
- **Промахи кешу (`L1-dcache-load-misses`):** Впали з 1.09 млрд до **69 млн**. Завдяки послідовному читанню даних по рядках, апаратний prefetcher зміг підвантажувати кеш-лінії заздалегідь.

### 4.3. Зміни на FlameGraph після оптимізації

Структурно оптимізований FlameGraph виглядає подібно до початкового — функція множення візуально все ще найширша. Це пояснюється тим, що вісь X показує відносний час. Хоча час впав до 0.14 с, множення матриць (\(O(N^3)\)) відносно ініціалізації масивів (\(O(N^2)\)) все одно залишається найважчою частиною, тому і займає ~85–90% від цих 0.14 секунд. З'явилися блоки `[unknown]`, що є наслідком видалення компілятором frame pointers для вивільнення регістрів під обчислення (типово для `-O3`).

### 4.4. Порівняння енерговитрат та їх причина

Енерговитрати досліджуваної програми знизились із **~113 Дж** до **~3.5 Дж** (навіть при припущенні максимального навантаження AVX у 25 Вт).

**Причина різниці:** Процесор перестав витрачати час і енергію на "марне" простоювання в очікуванні даних з оперативної пам'яті (завдяки усуненню кеш-промахів). Векторизація дозволила виконати той самий обсяг математичних дій за значно меншу кількість тактів.
